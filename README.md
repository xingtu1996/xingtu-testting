## 一句话定位

收集「人怎么测 AI、AI 系统怎么被测坏」的真实问题与案例——不谈模型跑分，只谈测试实践里踩过的坑、判断依据和适用边界。

## 为什么单独建这个仓

测试 AI 和测试传统软件不是一回事。输出不确定、判据难写、失败不可复现——同一套断言在不同上下文可能给出相反结论。本仓不重复造评测框架，只做一件事：把「遇到什么问题 / 当时怎么判断 / 结论站不站得住」沉淀成可复用的案例。

## 核心内容

- **问题模式库**：AI 测试中最常见的失败类型（判据模糊、非确定性、数据污染、评测泄漏等），每条注明来源与验证程度。
- **案例拆解**：按统一模板记录真实或公开可核对的测试案例，区分「本机实测」与「公开资料整理」。
- **判据笔记**：一条测试结论要成立，需要哪些证据；什么情况下该判死、什么情况下是假阳性。

## 与相邻仓的边界

| 仓 | 管什么 | 不管什么 |
|---|---|---|
| `tokenhub-bench` | 模型能力的可复现跑分对比 | 不管测试实践里的问题与判断 |
| **xingtu-testting**（本仓） | 测试实践的问题、判断与案例 | 不做模型排行榜、不做评测框架 |
| `xingtu-agent-skills` | 可安装复用的技能 | 不记录测试失败案例 |

## 快速开始

```bash
git clone <仓库地址> xingtu-testting
cd xingtu-testting
# 案例模板在 cases/_TEMPLATE.md，复制后按小节填写
```

新增案例请先读 [`cases/_TEMPLATE.md`](cases/_TEMPLATE.md)：每条案例必须带**状态标注**与**证据来源**，没有证据的推断标 `design`，本机跑过并留痕的才标 `verified`。

## 案例状态标注（全仓统一）

| 状态 | 含义 |
|---|---|
| `design` | 仅设计/设想，未验证 |
| `public-source` | 公开资料整理，非本仓实测，需带原文链接与核对日期 |
| `verified` | 本机实测，有可核对的命令/输出/截图 |
| `production` | 生产环境在用 |

## 入库规范

- 案例一律实体脱敏：客户名、人名、内网域名、内部平台链路不入库。
- 数字必须标注来源与验证程度；二手星标数、价格会过时，不作为判据。
- 公开案例写清「谁做的 / 在哪核对 / 核对日期」，不包装成亲历实测。
