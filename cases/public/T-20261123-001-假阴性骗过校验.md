# T-20261123-001 · "没匹配"不等于"不存在"：校验工具的假阴性

- 状态：`verified`（自有坏例索引，已脱敏改写）
- 核对日期：2026-11-23

## 问题是什么

用命令行搜索工具做内容校验，输出为空 → 判定"内容丢了/没写进去"，差点触发一轮无谓返工；实际内容完好，是**校验工具自己产生了假阴性**。

## 背景与约束

- 触发场景：验证渲染结果是否含某段内容、变更是否已回写台账、错误是否已被修正。
- 约束：macOS 自带工具的正则方言与多字节处理有已知限制；"无匹配"与"确实不存在"从输出上无法区分。

## 当时怎么判断 / 怎么做

- **假阴性模式一**：BRE 模式下 `\|` 不是"或"运算（是 GNU 扩展），被当成字面字符匹配 → 多分支模式全废，静默无匹配。
- **假阴性模式二**：`-o` 提取多字节中文输出不可靠，命中也可能打不出来。
- **假阳性相邻模式**：用符号计数（数 `grep -c "🔴"`）当门禁结论，把汇总行里"🔴0"的零值计成命中 → 误判有红线项。
- 两次都是**换第二种方法复查**（脚本字符串计数 / ripgrep）才拿到真值；一天内同类问题复发，且后续一轮任务内又复发 3 次。

## 证据

- 本机实测：换用 python 字符串计数 / ripgrep 复查，原判定为"丢失"的内容实际都存在；符号计数改解析汇总行数字后结论正确。
- 来源：维护者自有坏例索引（含同日两次、后续三轮复发的记录），已去除文件名、编号、具体模式串等实体。

## 结论与适用边界

- **结论成立的前提**：校验工具的方言/编码限制未知或不可控；断言是"有/无"的二值判断。
- **核心判据**：凡"文件没写 / 内容丢了 / 工具没生效"这类结论，下判断前**必须换第二种方法交叉验证**。校验误报的代价是把好的当坏的返工，比不校验更贵。
- **做法**：中文内容断言优先脚本层字符串计数或 ripgrep；或运算用扩展正则；门禁结论只认结构化解析（取数字），不用符号计数。
- **换场景**：若工具链可控（统一 ripgrep + UTF-8），假阴性风险大幅下降，但"验证动作本身要被验证"的原则仍成立。
